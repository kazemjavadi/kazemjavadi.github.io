        • Master-slave
          • One node is designed as the master ⟶ This master is the authoritative source for the data and is usually responsible for processing any update to the data. ⟶ Other nodes are slave or secondaries ⟶ A replcatoin process synchronizes the slaves with the master
          • ✔ It is useful for scaling when we have read-intensive dataset.
          • ✘ It isn't such good scheme for database with heavy write traffic ⟶ although offloading the read trafic will help a bit with handeling the write load.
          • ✔ Read resilience.
          • ✘ The failure of master does eliminate the ability to handle writes until either the master is restored or a new master appointed.
          • ✔ Master-slave replication is useful even if we don't need to scale out. ⟶ We can think of the master-slave replicaiton as a single-server store with a hot backup.
          • ✘ Dark side is inconsistency. ⟶ We have the danger that different clients, reading differnt slaves because the changes haven't all propagated to the slaves. ⟶ In worst case, a client cannot read write it just made.
          • ✘ I we use master-slave replicatoin just for hot backup this can be a concern, because ⟶ if the master fails, any updates not passed on to the backup are lost.
        • Peer-to-peer
          • All replicas have equal weight. ⟶ All accept read and write.
          • ✔ We can ride over node failures without losing access to the data.
          • ✔ We can easily add nodes to improve our performance.
          • ✘ When we can write to two different places, ⟶ we run the risk taht two people will attempt to update the same record at the same time. ⟶ Write-write conflict (Two or more people attemptto update the same record at the same time)
          • ✔ inconsistency on read are transient, but inconsistency on writes are forever.
          • The replicas coordinate to ensure we avoid write conflict ⟶ cost of network traffic to coordinate the writes. ⟶ We don't need all the replicas to agree on the write, just majority ⟶ We can still survive losing a minority of the replica nodes.
          • Trade off consistancy for availability

Consistancy

* As soon as we start buildingsomething we havet to think about what sort of consistancy we need for our system.

  • Update consistancy
    • Write-write conflict ⟶ two people updating the same data item at the same time.
    • Maintaining consistancy in the face of concurrency are often described at the
      • Pessimistic ⟶ Preventing confilict from occuring
        • The most common pessimistic approach s to have write locks, so that in order to change a value we need to acquire a lock and system ensure that only one client can get a lock at a time.
        • ✘ Pessimistic cuncurency often leads to deadlocks, which are hard to prevent and debug.
      • Optimistic ⟶ Lets confilicts occur, but detects them and takes action to sort them out.
        • A common optimistic approach is a conditional update. ⟶ Any client that does an update tests the value just before updating to see if it's changed since his last read.
        • Any automated mrege of write-to-write conflicts is highly domain-specific and needs to be programmed for eah particular case.
      • Optimistic ⟶ Lets confilicts occur, but detects them and takes action to sort them out.
  • Read consistancy
    • Read-write conflict ⟶ inconsistent read ⟶ A read in the middle of the write. ⟶ locgical consistancy ⟶ Ensuring that different data items makes sense together.
      • ✔ Solution: to avoid the read-write conflict
        • Relational databases ⟶ Support the notion of transaction.
        • Aggregate-oriented databases ⟶ Support atomic update, but only within a single aggregate ⟶ Logical consistancy within an aggregate but not between aggregate
      • Inconsistency window ⟶ The length of time an inconsistency is present is called the inconsistency window.
      • Replicaiton consistency ⟶ Ensuring that the same data item has the same value when read from different replicas.
      • Eventually consistent ⟶ Any time nodes may have replication inconsistencies but if there are no further updates, eventually all nodes will be updated to the same value.
      • Stale data ⟶ Data that is out of the date.
      • Read-your-write consistency ⟶ Once you're made an update. You're guaranteed to continue seeing that update.
      • Session consistency ⟶ Within the a user session there is Read-your-write consistency
        • ✔ Solutions:
          • Sticky session ⟶ A session that's tied to one node. ⟶ Reduce the ability of the load balancer to do it's job.
          • Version stamp
  • Relaxing consistency ⟶ consistency is a good thing but sometimes we have to sacrifice it. ⟶ It is always possible to design a system to avoid inconsistencies, but often imposible to do so without making unbearable sacrifices in other characteristics of the system. ⟶ Different domains have different tolerance for inconsistency, and we need to take this tolerance into account as we make our decisions. ⟶ * Many systems forgo transactions entirely because the performance impact of the transactions is too high.
    • Relaxing Durability ⟶
      • There are cases where we may want to trade off some durability for higher performance. ⟶ If a database can run mostlly in memory, apply updates to its in-memory representation, and periodically flush changes to disk, then it may be able to provide substantialy responsiveness to requests. ⟶ The cost is that, in the database crash, any updatessince the last flush will be lost.
      • We can improve replication durability by ensuring that the master waits for some replicas to acknowledge the update before the master acknowledges it to the client. Obviously, however, that will slow down updates and make the cluster unavailable if slaves fail. ⟶ We have trade off.
      • Quarum ⟶ The more nodes we involves in a request, th ehigher is the chance of avoiding an inconsistency. ⟶ (This inequalities are written with a peer-to-peer distribution model in mind)
        • Ensuring strong consistency on write ⟶ W > N/2 ⟶ W: Number of nodes participating in the write. N: Number of nodes involved in the replication (replicatoin factor)
        • Ensuring we get latest data ⟶ W + R > N
* Cache ⟶ Is another form of replicaton ⟶ Essentially following master-slave distribution model.

consistency guarantes aren't something that's global to an application ⟶ We can usually specify the level of consistency we want with individual requests ⟶ This allow us to use weak consistency most of the time when it isn't an issue, but request strong-consistency when it is.

  • ACID transaction
    • Atomicity ⟶ All or nothing ⟶ A transaction must fully complete or not happen at all. ⟶ No partial update
    • Consistency ⟶ Valid state ⟶ A transacion must take the database from one valid state to other, following all rules, constraints, and relationships.

    • Durability ⟶ It's saved ⟶ Once a transaction is comitted, the changes are permanent, even if the system craches.
    the CAP theorem ⟶ Between three properties on consistency, availability and partition tolerance, we can only get two ⟶ In a system that may suffer partitions, as disributed systems do, you have to trade off consistency versus availability ⟶ This isn't a binary decision, often, we can trade off a little consistency to get some availability. ⟶ We can not solve it purely within the development team, we have to talk to domain experts.

Map-reduce pattern

  • Map-reduce is a pattern to allow computations to be parrallelized over a cluseter
    • Map ⟶ Read data from an aggregate and boils it down to relevant key-value pairs ⟶ Maps only read a single record at a time and can thus be parallelized and run on the node that stores the record.
    • Reduce ⟶ Take many values for a single key ⟶ (Output from map tasks) ⟶ and summarize them into a single output. ⟶ Each redeucer operates on the result of a single key, so it can be parallelized by key ⟶ Reducers that have the same form for input and output can be combined into pipelines. This improves parallelism and reduces the amount of data to be transferred. ⟶ Map-reduce operations can be composed into pipelines where the output of one reduce is the input to another operation's map.

Key-value databases

  • A key-value store is a simple hash table ⟶ Primarily used when all access to the database is via primary key ⟶ Think of a table in a traditional RDBMS with two columns, such as ID and NAME, the ID column being the key and NAME column storing the value. In an RDBMS, the NAME column is restricted to storing data of type string. ⟶ If the ID exists the current value is overwritten, otherwise a new entry is created.
  • The value is blob that the data store just stores, without caring or knowing what's inside. ⟶ It's the responsibility of the application to understand what was knowing what's inside. ⟶ It's the responsibility of the application to understand what was stored.
  • Since key-value stores always use primary=key access, they generally have great performance and can be easily scaled.
  • Suitable use cases
    • Sotring session information
    • User profile, preferences ⟶ userId, username, language, color, timezone, ...
    • Soping card data ⟶ Shopping carts tied to the user. As we want the shopping carts to be available all the time, across browsers, machines, sessions, ...
  • When not to use
    • Relationships among data
    • Multioperation transactions ⟶ If you're saving multipe keys and there is a failure to save any one to them, and you want to revert or roll back rest of the operations.
    • Query by data
    • Operations by sets ⟶ Since operations are limited to one key at a time, there is no way to operate upon multiple keys at the same time. If we need to operate upon multiple keys, we have to handle this from the client side.

Document databases

  • Documents are the main concept in the document databases. ⟶ The database stores and retrieves documents, which can be XML, JSON, BSON, and so on.
  • Document databases store documents in the value part of the key-value store ⟶ Think about document databases as key-value store where the value is examinable.
  • The schema of the data can differ across documents, but these documents can still belong to the same collection ⟶ Unlike an RDBMS where every row in a table has to follow the same schema.
  • In documents, ther are no empty (null) attribute; if a given attribute is not found, we assume it was not set or not relevant to the document.
  • Transactions at the single-document level are known as atomic transactions
  • Document databases provide different query features. ⟶ We can query the data inside the document without having to retrieve the whole document by its key and then introspect the docuement.
  • Suitable use cases
    • Event logging
    • Content management systems, Blogging platforms
    • Web analytics or real-time analytics
    • E-Commerce Applications ⟶ E-Commerce applications often need to have flexible schema fro products and orders, as well as the ability to evolve their data models without expensive database refactoring or data migration.
  • When not to use
    • Complex transactions spanning different operations
    • Queries against varying aggregate structure

Graph databases

  • Since graph databases are operatig on connected nodes, most graph database solutions usually do not support distributing the nodes on different servers ⟶ within a asingle server, data is always consistent. ⟶ Graph databases ensure consistency through transactions. They do not allow dangling relationships. The start node and end node always have to exist, and nodes can only be deleted if the don't ave any relationaships attached to them.
  • In NoSQL databases, one of the commonly used scaling techniques is sharding, where data is split and distributed across different servers. ⟶ With graph databases sharding is difficult, as graph databases are not aggregate-oriented but relationship-oriented. ⟶ Since any given node can be related to any other node, storing related nodes on the same sever is better for graph traversal. ⟶ Traversing a graph when the nodes are on different machines is not good for performance. ⟶ There are three ways to scale graph databases ⟶
    • Since machines now can come with lost of RAM, we can add enough RAM to the server so that the working set of nodes and relashanships is held entirely in memory. ⟶ This technique is only helpful if the dataset that we are working with fit in a realistic amount of RAM.
    • We can improve the read scaling of the database by adding more slaves with readonly access to the data, with all the writes going to the master.
    • When the dataset size make replication impractical, we can shard.
    • Suitable use cases
      • Connected data ⟶ Any link-rich domain is well suited for graph databases.
      • Routing, Dispatch, and Location-Based Services
      • Recommendation Engines
    • When not to use
      • When we want to update all or subset of entities.

Schema migration

  • Databases with strong schemes, such as relational databases, can be migrated by saving each schema changes, plus its data migration, in a version-controlled sequence.
  • Schemaless databases still need careful migration due to the implicit schema in any code that access the data. ⟶ Schemaless databases can use the same migration techniques as databases with strong schemas. ⟶ Schemaless databases can also read data in a way that's tolerant to changes in the data's implicit schema and use incremental migration to update data.

Polyglot persistence

  • Different databases are designed to solve different problems. ⟶ Using a single database engine for all the requiremetns usually leads to non-performant solutions.
  • Database engines are designed to perform certian operations on

    certain data structures

     and data amounts very well. ⟶ It is not necessary for the applicatoin to use a single data store for all of its needs, since different databases are built for different purposes and not all problems can be elegantly solved by a single database.
  • Polyglot programming express the idea that applicatoins should be written in a mix of languages to take advantage of the fact that different languages are suitable for tackling different problems. ⟶ Complex applications combine different types of problems, so picking the right language for each job may be more productive than trying to fit all aspects into a single language. ⟶ Polyglot persistence ⟶ Hybrid approach to persistence.
  • Encapsulating data access into services reduces the impact of data storage choices on other parts of the system.
  • Adding more data storage technologies increases complexity in programming and operations, so the advantages of a good data storage fit need to be weighed against this complexity.

Beyond NoSQL

  • File systems
    • They don't advertise any interal structure, so they are more like key-value stores with a hierarchic key
    • They provide little control over concurrency other than simple file locking. ⟵ It is similar to the way NoSQL only provides locking within a single aggregate.
    • Files work very well for sequential access, such as steaming, which can be handy for data which is append-only
    • File systems work best for a relatively small number of large files that can be processed in big chunks, perferably in a streaming style. ⟶ Large numbers of small files generally peform badly.
    • Fles provide no support for queries without additional indexing tools.
  • Event Sourcing
    • Event sourcing is an approch to persistence that concentrate on persisting all the changes to a persistent state rather than persisting the current application state itself. ⟶ It's an architectural pattern ⟶ quite well with most persistence technologies.
    • With an event-sourced system, the first step is to constrcut an event object that captures the information about the change ⟶ This event object is stored in a durable event log. ⟵ Finally we process the event in order to update the applicaton's state
    • As consequence, in a an event-sourced system we store every event that' caused a state change of the system in the event log, and the applicatoin state is entirely derivable from this event log. ⟶ At any time, we can safely throw away the applicaiton state adn rebuild the event log.
    • In theory, event logs are all we need because we can always recreate the applicatoin state whenever we need it by replaying the event-log. ⟶ In practice, this may be too slow. ⟶ As a result, it's usually best to provide the ability to store and recreate the applicatoin state in a snapshot ⟶ A snapshot is designed to persist the memory image optimized for rapid recovery of the state. ⟶ It is an optimized aid, os it should never take precedence over the event log for authority on the data. ⟶ How frequently we take a snapshot depends on our uptime needs.
    • We can broadcast events to multiple systems, each of which can build a different applicatoin state for different purposes.
    • Event sourcing is also an effective platform for analyzing historical information
  • Memory Image
    • One of the consequences of event sourcing is that the event log becomes the definitive persistent record. ⟶ But it is not necessary for the applicaiton state to be persistent. ⟶ This opens up the option of keeping the application state in memory using only in-memory data structures. ⟶ Performance
  • Version Control
    • Version controll allows many people on a team to coordinate their modifications of a complex interconnected system, with the ability to explore past states of that system and alternative realities through branching.
    • Version control systems are built on top of the file systems ⟶ They are not designed for applicatoin data storage, so are awkward to use in that context. ⟶ They worth considering for scenarios where their timeline capabilites are useful.
  • XML Databases
    • Run queries with XPath and XQuery
  • Object Databases
    • When object-oriented programming started its rise in popularity, there was a flurry of interest in object-oriented databases. ⟶ The focurs here was the complexity of mapping from in-memory data structures to relational tables. ⟶ The idea of an object-oriented database is that we avoid this complexity. ⟶ The database would automatically manage the storage of in-memory structures onto disk. ⟶ We could think of it as a persistent virtual memory system, allowing us to program with persistence yet without taking any notice of a database at all. ⟶ Close integration with the applicaiton.
