NoSQL Distilled

Posted on April 24, 2025 | In: NotSQ

NoSQL born out of need to handle larger data volumes through cluster

  • NoSQL generally applied to
    • Non-relational databases
    • schemaless data
  • NoSQL trade off consistancy for
    • Productivity ⟶ Application development Productivity ⟶ No need mapping between in-memory data structure and relational databases (No impedance mismatch)
    • Performance ⟶ Cluster ⟶ Relational databases suitable for Single machine ⟶ NoSQL databases suitable for multiple machine (cluster) ⟶ Better for big data scenario
  • Common characteristics of the NoSQL databases
    • ✘ Not using relational model
    • ✔ Running well on clusters ⟶ Size and performance
    • ✔ Open source
    • ✔ Schemaless ⟶ No impedance mismatch
  • Relational databases
    • Consistancy ⟶ transaction
      • ✘ Relational databases use ACID transactions that inherently clashes with a cluster environment
    • Integratiokn ⟶ Shared database ⟶ multiple application, single database scenario
      • ✘ Different applications have different structure and performance needs]
        • ✔ Solution ⟶ Service-oriented architecture ⟶ Shift from integration databases to the application databases
    • Standard model ⟶ For different relational databases core mechanisms remain same
    • Impedance mismatch ⟶ Differnce between the relational model and in-memory data structure
      • ✔ Solution ⟶ ORM (Object-relational mapping) frameworks
  • Scale
    • Scale up ⟶ hardware
    • Scale out ⟶ cluster

Aggregate data model

● Data model ⟶ The model through which we perceive and manipulate data ≠ Storage data model
  • Data model
    • Aggregate ignorant ⟶ Relational
    • Aggregate oriented ⟶ NoSQL
      • Key-Value
      • Document
      • Column-Family
      • Graph (Aggregate ignorant)
  • Aggregate
    • Data manipulation ⟶ Update aggregate with atomic operations
    • Management of consistancy (transation) ⟶ Communicate with our data storage in therms of aggregate
  • Transactions
    • Relational databases ⟶ Aggregate ignorant databases ⟶ ACID transaciton ⟶ Any combination of rows
    • NoSQL databases ⟶ Aggregate oriented databases
      • ✘ Multiple aggregate ⟶ No ACID transaction
      • ✔ Single aggregate ⟶ Atomic manipulation
  • NoSQL databases (aggregate oriented)
    • Key-Value
      • Strongly aggregate oriented
      • Aggregate is opaque to the database
      • Having Key or ID to get data
    • Document
      • Strongly aggregate-orineted
      • Having a Key or ID to get the data
      • Able to see structure of aggregate
      • Query based on fileds in the aggregate
      • Retrivepart of the aggregate
      • Create index based on the content of the aggregate
    • Graph
      • Small records with complex interconections
      • In relational databases performance is poor for highly connected data model ⟶ Graph databases make teraversal along the relationships very cheap. ⟶ Graph database shift most of the work of navigating relationships from query time to insert time ⟶ for situations where quering performance is is more important that insert speed.
      • Graph database except most of our work be navigating relationship
      • More likely run on single server
  • Materialized view ⟶ Views that are computed in advance and cached on disk ⟶ Two strategies to building view
    • Update the materialized view at the same time we update the base data
    • Batch jobs to update the materialized views at regular intervals

Aggregate-oriented databases make inter-aggregate relationships more difficult to handle than intra-aggregate relationships.

Distribution Models

Aggregate-oriented databases fits well with scale out ⟶ because ⟶ aggregate is natural unit to use for distribution.

⚠ Running over a cluster intoduces complexity, so it is not something to do unless the benfis are computing.

  • Data distribution
    • Replicatoin ⟶ Same data over multiple nodes
      • Types of replicatoin data distribution
        • Master-slave
          • One node is designed as the master ⟶ This master is the authoritative source for the data and is usually responsible for processing any update to the data. ⟶ Other nodes are slave or secondaries ⟶ A replcatoin process synchronizes the slaves with the master
          • ✔ It is useful for scaling when we have read-intensive dataset.
          • ✘ It isn't such good scheme for database with heavy write traffic ⟶ although offloading the read trafic will help a bit with handeling the write load.
          • ✔ Read resilience.
          • ✘ The failure of master does eliminate the ability to handle writes until either the master is restored or a new master appointed.
          • ✔ Master-slave replication is useful even if we don't need to scale out. ⟶ We can think of the master-slave replicaiton as a single-server store with a hot backup.
          • ✘ Dark side is inconsistancy. ⟶ We have the danger that different clients, reading differnt slaves because the changes haven't all propagated to the slaves. ⟶ In worst case, a client cannot read write it just made.
        • Peer-to-peer
    • Sharding ⟶ Different data on different nodes
      • Points
        • Busy data store is busy because differnt people are accessing different parts of the dataset. In this circumestances we can support horizontal scalability by putting different data parts of the data onto different servers. We have to ensure that data that's accessed together is clumped together on the same node.
        • Aggregate orientation in Sharding data distribution comes really handy ⟶ The whole point of aggregate is that we design them to combine data that's commonly accessed together.
          • ✔ If we know that most accesses of certian aggregates are based on a physical location, we can place the data close to where it's being accessed.
          • ✔ In some cases, it's useful to put aggregates together if we think they may be read in sequence.
        • Imporve read and write performance ⟶ horizontaly scale write.
        • Sharding does
        • little
          • to imporove resilience when used alone. ⟶ a node failure makes that's shard data unavailable ⟶ like single server solution
          • ✘ With single server it's easier to pay the effort and cost to keep that server up and running ⟶ Sharding alone is likely to decrease resilience.
        • ✔ It is best to start single server and use sharding once our load projection clearly indicate that we are running out of headroom ⟶ We should use sharding well before we need to. When we have enough headroom to carry out the sharding
    • Single server
